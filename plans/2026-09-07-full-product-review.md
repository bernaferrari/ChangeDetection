## What the requested behavior means

Normal monitoring should use a clearly displayed **15-minute–7-day interval** with persistent scheduling. Android WorkManager schedules opportunistically: Doze, power management and constraints can delay a run. Therefore the product should say approximately when a check is eligible and when it last actually succeeded, rather than promise exact wall-clock execution. [Android periodic-work contract](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest).

Turbo should be a user-started session with **30-second cadence and other supported choices, a three-hour deadline, actual completion status, and one authoritative Stop operation**. Current choices are 15s, 30s, 1m and 2m. The three-hour default exists, but worker cancellation, lifecycle state and widget extension undermine a strict three-hour cap. A foreground service alone does not make independently queued jobs run on time.

The existing schedule is global, applying to all enabled sites. If different pages must run at different intervals, that requires an explicit product/model change; it is not currently implemented.

## Visual design and M3 Expressive

**Preserve:** actual MaterialExpressiveTheme and expressive motion scheme, Android dynamic colors and tonal fallback ([ChangeDetectionTheme.android.kt:58](/Users/bernardoferrari/Documents/android/ChangeDetection/composeApp/src/androidMain/kotlin/com/bernaferrari/changedetection/ui/theme/ChangeDetectionTheme.android.kt:58)); connected button groups; labeled adaptive navigation ([NavigationSuite.kt:79](/Users/bernardoferrari/Documents/android/ChangeDetection/composeApp/src/commonMain/kotlin/com/bernaferrari/changedetection/ui/navigation/NavigationSuite.kt:79)); grouped site rows with status semantics and theme-driven selection/press motion ([SiteRow.kt:107](/Users/bernardoferrari/Documents/android/ChangeDetection/composeApp/src/commonMain/kotlin/com/bernaferrari/changedetection/ui/main/SiteRow.kt:107)); generally clear URL fields, loading/empty/error states and destructive confirmations.

## Architecture and tests

The reusable core is worth keeping: SyncEngine, repositories, platform interfaces, screenshot browser injection, Room, DataStore, Compose and adaptive navigation. The largest architectural defect is **multiple owners of the same monitoring session** (service, ViewModel, WorkManager, preferences and widget), not the choice of Kotlin Multiplatform.

Create one session controller and one awaited check runner. WorkManager should invoke the runner for normal opportunistic work; Turbo should invoke it under the foreground session. All UI should observe the controller's real state. Use per-site execution exclusion across entry points, structured cancellation, explicit retry state, and immutable check results. Preserve the useful existing transaction/progress/screenshot seams instead of a wholesale rewrite.

Split large screen implementations only when it makes their states independently testable. MainScreen is still about 850 lines, but reducing line count is lower priority than fixing false status and data loss. Existing plans 001–005 are stale in places: expressive theme and screen extractions already exist; don't blindly reapply the older plans.

The current local build and 114 passing host tests establish a useful compilation/unit baseline. They do not exercise Android foreground promotion or the actual SQLite relationships in the failing edit journey. The critical missing tests are lifecycle/integration tests. [WorkTest.kt:12](/Users/bernardoferrari/Documents/android/ChangeDetection/composeApp/src/androidUnitTest/kotlin/com/bernaferrari/changedetection/WorkTest.kt:12) is an arithmetic placeholder; [QuickMonitorUiTest.kt:26](/Users/bernardoferrari/Documents/android/ChangeDetection/composeApp/src/androidInstrumentedTest/kotlin/com/bernaferrari/changedetection/ui/main/QuickMonitorUiTest.kt:26) verifies a site row, not Turbo execution. The explicit host-test source-directory allowlist also omits the extensions test directory ([build.gradle.kts:167](/Users/bernardoferrari/Documents/android/ChangeDetection/composeApp/build.gradle.kts:167)), so adding a test file there does not make it part of this suite.

Required gates before declaring the app working:

1. Clean-checkout Android build, required native CI, host tests and device tests actually executed. Compile-only device tests are insufficient.
2. Fresh install → add synthetic site → baseline → recurring schedule enabled/displayed → changed response → saved version and notification → notification opens the correct pair.
3. Rename and Keep history preserve snapshots; migrated unknown hashes survive pruning; Start fresh failure preserves the pre-operation state.
4. Virtual-clock Turbo tests for 30s cadence, slow checks, retry, multi-site load, selection changes and exactly one session; every stop path/expiry prevents subsequent session checks.
5. On-device foreground screenshot work, screen-off/Doze/constraints, process death, offline recovery and notification denial. Report delayed checks honestly.
6. Memory/storage stress with changing large HTML and screenshots. Prove bounded cache/retention and useful errors on storage exhaustion.
7. Chronology/deep-link tests and accessible compact/expanded screenshots with large text. Repair stale semantic assertions rather than merely compiling them.

## Product direction, separate from defects

**Make meaningful changes the default.** Full-page screenshots with binary inequality and zero threshold will alert for rotating promotions, clocks and unrelated page movement ([AndroidScreenshotSyncer.kt:165](/Users/bernardoferrari/Documents/android/ChangeDetection/composeApp/src/androidMain/kotlin/com/bernaferrari/changedetection/sync/AndroidScreenshotSyncer.kt:165), [ContentHasher.kt:48](/Users/bernardoferrari/Documents/android/ChangeDetection/composeApp/src/commonMain/kotlin/com/bernaferrari/changedetection/util/ContentHasher.kt:48)). Introduce per-monitor text/visual choice and a preview, then region selection/ignore rules or tolerance. This is a multi-day design/implementation change with a real risk of over-filtering; preserve an explicit any-change mode.

**Make monitoring health the main product surface.** Show last successful observation, requested cadence, next eligible check and delay reason. A compact health summary is more valuable here than a decorative instrument. This direction builds on the existing status models and fixes 02/20/23 rather than adding another dashboard.

**Choose the reliability contract explicitly.** For an on-device/private app, best-effort normal scheduling with transparent delays is a reasonable product. If exact checks must happen while the phone is off, offline or force-stopped, that requires an always-on external execution service and a different privacy/operating model; it cannot be supplied by a prettier Android timer.

## Recommended order

1. Fix foreground crash, credential hygiene and reproducible verification.
2. Protect history: update/upsert, migration deduplication, atomic Start fresh, real Room tests.
3. Establish normal monitoring during setup; unify schedule defaults and commit/validation behavior.
4. Replace Turbo's enqueue loop with session-owned execution; unify Stop, deadline, timeout, process recovery and widgets.
5. Correct health/read/chronology state; add pause/mute/Open page and actionable Turbo outcomes.
6. Bound memory/storage and improve meaningful-change detection.
7. Finish with rendered M3/accessibility polish, backed by a working app and real lifecycle tests.
